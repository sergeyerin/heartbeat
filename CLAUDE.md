# CLAUDE.md — heartbeat

Единственный источник правды о проекте для всех агентов из `~/.claude/agents`
(библиотека `my-claude-agents`). Агенты читают этот файл первым. Если структура
проекта меняется — обновлять здесь же, иначе агенты работают с неверными
допущениями.

## Что это

Телеграм-бот «дневник аритмии». Главная ценность — регистрация эпизода в одно
нажатие в тот момент, когда человеку физически плохо. Всё остальное
(тяжесть, пульс, симптомы, причины, заметка, время окончания) — опциональные
уточнения, которые можно заполнить позже или не заполнять вовсе.

Публичный репозиторий: https://github.com/sergeyerin/heartbeat
Бот открыт всем пользователям Telegram, дневники изолированы по `user_id`.

## Стек

- Python 3.12, `python-telegram-bot[job-queue]` >= 21.4 (async), long polling
- SQLite через stdlib `sqlite3` (WAL), без ORM и без миграционного фреймворка
- Docker + docker compose, `network_mode: host`, том `./data`
- Внешних API нет: ни LLM, ни аналитики, ни сторонних сервисов

## i18n — где лежат переводы

Единый файл `i18n.py`, не каталог с json. Структура: `STRINGS[ключ][язык]`,
плюс `MONTHS`, `WEEKDAYS`, `CSV_HEADER` и `vocab.SYMPTOMS/TRIGGERS/SEVERITY`.

Поддерживаемые языки: **ru, en** (`i18n.SUPPORTED`). Fallback — `en`.

Правила, которые проверяет `smoke_test.py` (не ослаблять):
- каждый ключ существует в обоих языках;
- набор плейсхолдеров в переводе совпадает с эталонным (`i18n.FALLBACK`);
- все коды симптомов/причин переведены на все языки, уровней тяжести ровно три;
- подписи кнопок нижней плашки уникальны по всем языкам — текст кнопки
  приходит обратно от Telegram, одинаковые подписи сделали бы нажатие
  неоднозначным;
- в БД хранятся только коды (`skip`, `coffee`), подписи — слой отображения.

**Хардкод пользовательских строк в `bot.py`/`report.py` запрещён**: любая новая
фраза добавляется в `i18n.STRINGS` сразу на ru/en.

## Модель состояний эпизода

Понимать до любой правки `bot.py`/`db.py`:

| Состояние | Признак в БД | Поведение |
|---|---|---|
| идёт (active) | `ended_at IS NULL`, `COALESCE(confirmed_at, started_at)` свежее `STALE_AFTER_MIN` | блокирует второй эпизод, ловит свободный ввод |
| забыт (stale) | `ended_at IS NULL`, подтверждение старше `STALE_AFTER_MIN` | НЕ блокирует новый эпизод, НЕ ловит ввод, в отчёте отдельной строкой, в средние длительности не входит |
| закрыт | `ended_at` задан, `end_approx = 0` | полноценная длительность |
| закрыт примерно | `ended_at` задан, `end_approx = 1` | длительность с «~», отдельная колонка в CSV |

Инварианты:
- **Действие применяется только к эпизоду в подходящем состоянии.** Инлайн-кнопки
  живут в истории чата вечно и нарисованы в том состоянии, которое было на момент
  отправки. Поэтому `e`/`sh` требуют эпизода, который идёт **прямо сейчас**
  (`NEEDS_ACTIVE`:
  открытый и не забытый — «отпустило сейчас» на забытом эпизоде записало бы
  ровную многочасовую длительность как точную), `ap`/`apm`/`go`/`unk` —
  открытого (`NEEDS_OPEN`), `ro` — закрытого (`NEEDS_CLOSED`). Вторым рубежом
  состояние проверяется в самом `UPDATE` в `db.close_episode`,
  `db.reopen_episode`, `db.shift_start` и `db.confirm_still_on` — все четыре
  возвращают `None`, если состояние уже изменилось. Без этого нажатие на старую
  карточку перезаписывало записанное время окончания.
- **Деструктивное действие требует свежего одноразового токена.** Инлайн-кнопки
  живут в истории чата вечно, поэтому `/forget` (весь дневник), `dy` (эпизод) и
  `nc` без отложенного текста (заметка) принимают только токен, выданный тем же
  диалогом: `fy:<token>`, `dy:<id>:<token>`, `nc:<id>:<token>`. Устаревший токен
  → «подтверждение устарело». Одно холодное нажатие на старую кнопку стирало
  весь дневник — это нашёл тим-лид исполнением, когда три круга ревью прошли
  мимо. В подтверждении безопасный выбор стоит первым, деструктивный вторым.
- **Любое значение из `callback_data` — недоверенное.** Оно сверяется с набором,
  из которого кнопка вообще могла его предложить (`_arg`/`_row_id`/`_episode_id`,
  `DURATION_CHOICES`, `SHIFT_CHOICES`, `SEVERITY_LEVELS`, `REPORT_PERIODS`,
  `vocab.*_CODES`, `("sym", "trg")` для меню), а не просто приводится к `int`.
  Идентификаторы дополнительно ограничены `SQLITE_MAX_INT`: число, не влезающее
  в 64 бита, роняло `sqlite3` необработанным `OverflowError`. Принадлежность
  строки проверяется до любого побочного эффекта — в том числе до перевода бота
  в режим ожидания ввода (`db.get_med`).
- **Отображение переживает неожиданные данные в базе.** Словари подписей
  читаются через `.get`: чужое значение портит одну строку, а не всю сводку дня.
- `ended_at` никогда не раньше `started_at` (клампится в `db.close_episode`);
- начало не уезжает в будущее (`db.shift_start`);
- **живая карточка — одна на эпизод**: её `message_id` хранится в
  `episodes.card_msg`, обновляется раз в `CARD_TICK_SEC` (60 с) задачей
  `tick:<user>:<episode>`, и при отправке новой карточки у прежней снимаются
  кнопки. Это же лечит корень проблемы со старыми кнопками: раньше каждая
  карточка была новым сообщением, и все они оставались нажимаемыми.
  **`_cancel_reminder` снимает только напоминание** — `_schedule_reminder`
  начинается с отмены прежнего, и если бы она снимала и обновление, то
  планирование напоминания убивало бы только что созданную живую карточку.
  Для «эпизод перестал идти» есть `_stop_live`;
- **«текущий эпизод» определён однозначно**: выборки упорядочены по
  `started_at DESC, id DESC`. Время хранится с точностью до секунды, и без
  тай-брейкера два эпизода, начатых в одну секунду, делали выбор произвольным —
  заметка или пульс могли уйти не в ту запись;
- **отказ не должен врать**: если перерисовать карточку не удалось (сообщение
  старше 48 часов правке не поддаётся), `_refresh` досылает свежую новым
  сообщением. Иначе всплывающая подсказка говорит «обновил карточку», а человек
  остаётся с неработающей кнопкой;
- **всякий лимит длины текста считается в UTF-16-единицах** (`i18n.utf16_len`,
  обрезка — `trim_utf16`), а не в символах: эмодзи вне BMP — один символ, но две
  единицы, и по `len()` лимит давал вдвое больший запас, чем есть. Это касается
  `db.MAX_NOTE_*`, `bot.TG_TEXT_LIMIT`, `bot.MED_NAME_LIMIT` и
  `report.FEED_NOTE_LIMIT`. Новый лимит на пользовательский текст добавлять
  только так же;
- длина заметки ограничена (`db.MAX_NOTE_CHUNK` на сообщение,
  `MAX_NOTE_TOTAL` на эпизод), а длинные тексты режутся на отправляемые части
  (`bot._split`, он делит слишком длинную строку, а не обрезает её): лимит
  сообщения Telegram — 4096 единиц, и текст, не влезающий в него, не
  отправляется вообще;
- **переполнение заметки не проглатывается молча и не лечится разрушением**:
  `db.append_note` возвращает статус, при `NOTE_FULL` бот ничего не пишет, но
  **текст остаётся у него**, и первая кнопка его сохраняет, вытесняя самое
  старое начало заметки (`db.append_note_dropping_oldest`). Записать «пульс 210,
  потерял сознание» и ответить «заметка добавлена» недопустимо — но и предлагать
  «удалите всё записанное и пришлите заново» единственным выходом тоже:
  человек терял записанные симптомы, а присланный заново текст уезжал в новый,
  выдуманный эпизод, потому что ожидание ввода к тому моменту снималось;
- «⏳ Ещё идёт» двигает `confirmed_at`, но **не** `started_at` — приступ может
  длиться часами, и длительность считается от начала;
- время окончания не выдумывается: если его нет, эпизод остаётся без него.

## Предохранители публичного бота

Бот открыт всем и однопроцессный, поэтому один человек не должен мешать
остальным. Измеренные сценарии и что их держит:

| Чем грозило | Предохранитель |
|---|---|
| 2000 нажатий «вернуть в работу» → 2000 открытых эпизодов и столько же задач за полсекунды | `MAX_OPEN_EPISODES` (10), проверяется и в `ro`, и при создании |
| неограниченный рост строк | `MAX_EPISODES_PER_USER` (5000) |
| поток нажатий | `MIN_ACTION_INTERVAL_SEC` (1.5 с) на эпизоды и лекарства |
| `/export` строит весь дневник в памяти и блокирует цикл событий | `EXPORT_COOLDOWN_SEC` (60 с) |
| `all_open_episodes()` выбирала ВСЕ открытые эпизоды всех пользователей при каждом старте | фильтр и `LIMIT` в SQL |

Отказ всегда объясняется словами — молчащий предохранитель человек читает как
поломку. Проверять при добавлении новых путей создания эпизодов: сейчас их
четыре (кнопка/команда, `nn`, `np`, геопозиция не создаёт).

## Геопозиция

Кнопка «📍 Место» живёт на нижней плашке, потому что запросить геопозицию умеет
только reply-клавиатура — в инлайновой такого нет. Координаты пишутся в
`episodes.lat/lon`, видны ссылкой на OpenStreetMap в карточке (без аккаунта и
трекинга, в отличие от Google Maps) и отдельными колонками в CSV.

Это повышение класса данных: к симптомам и пульсу добавляется «где человек
бывает». Поэтому координаты обязательно должны сниматься кнопкой «📍 Убрать
место» на карточке и удаляться вместе со всем остальным в будущем `/forget`.

## Что сознательно НЕ делаем

- **Вложений (ЭКГ, фото, PDF) бот не хранит.** Сценарий разбирался и отвергнут:
  ЭКГ из поликлиники уже есть в поликлинике, отчёт холтера — у назначившего его
  кардиолога, то есть копия в боте избыточна. Не избыточен только один случай —
  домашний одноканальный прибор, снимающий ленту в момент приступа, — а прибора
  у пользователя нет. Присланный файл получает вежливый отказ (`on_file`): без
  него человек получал тишину и делал вывод, что бот сломан. Если прибор
  появится, возвращать имеет смысл целиком: таблица, счётчик на карточке,
  колонка в CSV и команда выгрузки файлов за период.
- **Бот не интерпретирует данные.** Никакой автоматической расшифровки, оценок
  «стало хуже», порогов и подсказок, зависящих от записанных значений.
  Интерпретация ЭКГ — функция медицинского изделия; ошибка в сторону «всё в
  порядке» дороже любой пользы. Полный список запретов — в разделе про
  безопасность ниже.

## Проектные риски — обязательный чек-лист для `security`

1. **Данные о здоровье.** Эпизоды, пульс, симптомы, названия лекарств,
   свободные заметки. Утечка в логи, в чужой чат или в сообщение об ошибке —
   Blocker.
2. **Изоляция арендаторов.** Каждый запрос в `db.py` обязан фильтровать по
   `user_id`. `callback_data` управляется пользователем: любой id из него
   недоверенный, проверять владение эпизодом перед действием.
3. **Допущение `chat_id == user_id`** в напоминаниях (`_schedule_reminder`) —
   верно только для приватных диалогов; при любом расширении на группы это
   отправка медданных не туда.
4. **CSV-экспорт** попадает в Excel: заметка, начинающаяся с `=`, `+`, `-`, `@`,
   это потенциальная формульная инъекция. Закрыто `report.csv_safe`, который
   применяется ко **всем** пользовательским колонкам (заметка, симптомы,
   причины, название лекарства) — проверять при добавлении новых колонок.
5. **Публичный бот без allowlist**: неограниченный рост строк и job'ов от одного
   пользователя, деградация для остальных в однопроцессном дизайне.
6. **Удаление своих данных** — право пользователя; отсутствие такой возможности
   считать находкой, а не фичей.

Раздела про безопасность ИИ-контента (Section 10) к проекту не применимо:
LLM в боте нет, тексты статические. Указывать это явно, а не молча пропускать.

## Типовые отказы — ориентир для `debugger`

- `409 Conflict` от Telegram — запущено два инстанса на один токен.
- «unable to open database file» — том `./data` не смонтирован или права не у
  процесса контейнера (поэтому контейнер работает под root, см. `Dockerfile`).
- «Job queue недоступна» в логе при старте — не установился extra
  `python-telegram-bot[job-queue]`, напоминания молча выключены.
- Время в сводках в UTC вместо локального — в образе нет `tzdata` или не задан
  `TZ`.
- «Message is too long» от Telegram — где-то считают длину в символах вместо
  UTF-16-единиц (`i18n.utf16_len`).
- «message is not modified» при нажатии той же кнопки — норма, не ошибка.

## UX-принципы — ориентир для `ux`

1. Регистрация эпизода стоит одно нажатие. Любое изменение, добавляющее шаг
   между «началось» и «записано», отклоняется.
2. Человеку в момент приступа плохо: никаких обязательных полей, никаких
   многошаговых диалогов на пути к записи.
3. Бот не рассчитывает на память пользователя: спрашивает сам, но спрашивает
   один раз, без навязчивых повторов.
4. Бот не выдумывает данные. «Неизвестно» честнее подставленного нуля.
5. Копия на обоих языках сразу, иначе изменение не принимается.

## Workflow

Применяется процесс из `my-claude-agents/README.md`. Особенности проекта:

- Отдельного агента `test-writer` в библиотеке нет — **тесты входят в
  поставку `coder`**. Для `tech-lead` это означает: проверять не наличие агента,
  а наличие новых проверок в `smoke_test.py`/`flow_test.py` и зелёный прогон
  обеих команд.
- Workflow D (изменение промптов) неприменим: промптов нет.
- `product` и `ux` обязательны для изменений, видимых пользователю; для
  изменений внутри слоя данных — нет.
